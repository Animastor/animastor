1. Общая архитектура

┌─────────────────────────────────────────┐ │ runtime-loop (5s tick) │ │ reconcile-цикл (60s) ←─── CLEANUP_LOCK │ └────┬────────────┬──────────────┬────────┘ │ │ │ ┌────▼───┐ ┌────▼────┐ ┌──────▼───────┐ │Scheduler │ │Counter │ │Prometheus │ │(tick()) │ │Reconcil.│ │Metrics │ └────┬───┘ └─────────┘ └──────────────┘ │ ┌──────────▼──────────────────────┐ │ dispatch-engine.js │ │ lease + quota + circuit-break │ │ + retry-budget + fairness │ └──────────┬──────────────────────┘ │ ┌───────────────▼──────────────────┐ │ orchestrator.js (FACADE) │ │ markDirty / beginStage/ │ │ completeStage / failStage │ │ resetScenes / reconcile │ └──────┬──────────────┬──────────┘ │ │ ┌──────▼──┐ ┌─────▼──────────┐ │ state.js│ │audio-orch.js │ │(per-asset) │(phase machine) │ └─────────┘ └────────────────┘ │ │ ┌──────▼──────────────▼──────────┐ │ scene-orchestrator.js │ │ executeAudio/Image/Video │ └───────────────────────────────┘

Система оркестрации Animastor построена на трёх уровнях абстракции:

  • Runtime Loop — сердце системы. Каждые 5с запускает scheduler tick, каждые 60с — reconcile cycle.
  • Dispatch Engine — единая точка входа для отправки задач на GPU. Управляет lease, quota, circuit breaker, retry budget.
  • Orchestrator Facade — тонкий фасад над двумя state machine (assset state + audio-orch). Единственный, кто пишет состояние.
  • Scene Orchestrator — исполнитель. `executeAudioDispatch`, `executeImageDispatch`, `executeVideoDispatch`.
💡 Ключевое решение

Разделение на fast tick (5s) и slow reconcile (60s) — правильный архитектурный выбор. Tick содержит только лёгкие операции (scheduler + counter reconcil), а тяжёлое сканирование — в отдельном цикле с distributed lock.

2. Две state machine

✅ Верный дизайн

Разделение на per-asset (высокоуровневый статус) и audio-orch (детальный пайплайн) — правильная абстракция, позволяющая независимо отслеживать состояние каждого ассета.

Asset State Machine (state.js)

startScene() setSceneGenerating() completeStage() NEW ──────────→ PENDING ───────────────→ GENERATING ────────→ READY ↘ FAILED ──→ PENDING (re-dispatch) setSceneGenerating() DIRTY ────────────→ PENDING (regenerate)
StateСемантика
NEWТолько что создана, не начиналась
PENDINGОжидает диспетчеризации
GENERATINGВ процессе генерации
READYГотово (ассет на диске есть)
FAILEDОшибка генерации
DIRTYТребует регенерации (версия устарела)
PLACEHOLDERПлейсхолдер (аудио с синтезированной речью)

Audio-Orch State Machine (audio-orchestrator.js)

initPlaceholderReady() setGenerating() setWaitingChunks() NEW ─────────────────────→ PLACEHOLDER_READY ──────────→ GENERATING ──────────→ executeAudioDispatch() WAITING_CHUNKS ──→ MERGING ──→ DONE completeChunk() ↘ FAILED failWaitingScene() / watchdog FAILED ──→ GENERATING (scheduler re-dispatch) FAILED ──→ WAITING_CHUNKS (completeChunk, late chunk recovery)
PhaseСемантика
NEWНе инициализирована

MERGINGСклейка чанков в один файл (ffmpeg)

FAILEDОшибка

Инварианты (всегда true)

audio-orch.phase == DONE ⇔ asset.audio == READY audio-orch.phase == FAILED ⇒ asset.audio == FAILED или PENDING audio-orch.phase ∈ {WAITING_CHUNKS, MERGING} ⇒ asset.audio == GENERATING

Проверяются в reconcileCycle → checkAudioOrchInvariants().

4. Dispatch Engine — полный пайплайн

Dispatch-engine реализует полный конвейер перед отправкой job в GPU:

dispatchStage(): 1. Force pre-clear (если force=true) 2. Circuit breaker check 3. Duplicate/stale lease check 4. Quota acquisition (Lua atomic: GET+INCR) 5. Retry budget check 6. Fairness/starvation check 7. Lease acquisition (NX + TTL) 8. Set dispatch metadata 9. Journal event 10. Call orchestrator.dispatchStage() 11. Start lease renewal timer
✅ Сильные стороны

Lua EVAL для атомарного acquireQuota — элегантное решение race condition между проверкой лимита и инкрементом. FinalizeDispatch — единая точка финализации с идемпотентностью (completion marker). Lease renewal предотвращает преждевременное истечение аренды для долгих задач.

Поток финализации (finalizeDispatch)

finalizeDispatch(outcome): success → recordSuccess + circuitBreaker.recordSuccess НЕ расходует retry budget failure → recordFailure + circuitBreaker.recordFailure consumeRetryBudget ровно 1× cancelled→ без circuit breaker, без retry budget DISPATCH_CANCELLED
💡 Атомарность через Lua

CLAIM_FINALIZATION_SCRIPT — один Lua-скрипт проверяет metadata + lease owner, ставит completion marker, удаляет metadata/lease и освобождает quota. Всё атомарно.

7.3 Контракт фасада — инварианты каждой команды

КАЖДАЯ команда фасада гарантирует синхронность обоих state machine:

setSceneGenerating(audio): asset.audio = GENERATING if audio-orch exists AND NOT DONE → audio-orch = GENERATING if audio-orch is DONE → return { skipped: true, reason: 'already_done' } completeStage(audio): 1. verifyDispatchIdentity 2. handler (handleAudioCompleted) 3. version gate (PG) 4. if ok: asset.audio = READY AND audio-orch = DONE (синхронно) 5. if stale: asset.audio = DIRTY AND audio-orch → reset 6. finalizeDispatch (success/failure) failStage(audio): 1. verifyDispatchIdentity 2. validateAssetTransition(current → FAILED) 3. if ok: asset.audio = FAILED AND audio-orch = FAILED (синхронно) 4. if redispatch: asset.audio = PENDING 5. finalizeDispatch (failure) markDirtyScene(audio): if audio-orch DONE → deleteState (clean slate for regeneration) asset.audio = DIRTY PG: markStale setScenePending(audio): if audio-orch DONE → deleteState (clean slate) asset.audio = PENDING

8. Call Flows: 4 сценария TO-BE

Детальные диаграммы последовательностей из ORCHESTRATOR_ARCHITECTURE_WITH_AUDIO.md — как ДОЛЖНА работать оркестрация после полной реализации единого фасада.

8.1 Штатная генерация аудио

Scheduler tick → attemptDispatch() → shouldScheduleAssets(): asset=PENDING → stages=['audio'] → dispatchStage('audio') → acquireLease() → acquireQuota() → scene-orchestrator.executeAudioDispatch() ┌─ orchestrator.setSceneGenerating('audio') │ → asset.audio = GENERATING │ → audioOrch.setGenerating() # PLACEHOLDER_READY → GENERATING │ (или initPlaceholderReady если нет state) ├─ audioOrch.setWaitingChunks() ├─ audio.generateSceneAudio() → GPU hub (9 chunks) └─ return { dispatched: true } Chunk 0001 arrives → /gpu/task/result → handleTaskResult() → save file to disk → orchestrator передаётся в audioOrch.completeChunk() → audioOrch WAITING_CHUNKS (chunks_received=1) ... (chunks 0002-0008) Chunk 0009 arrives → audioOrch.completeChunk() → WAITING_CHUNKS → MERGING (all 9 chunks present) → ffmpeg merge → merged MP3 → MERGING → DONE → orchestrator.completeStage('audio') → handleAudioCompleted() → version gate (PG) → asset.audio = READY (синхронно с audio-orch DONE) → finalizeDispatch(success) → publishProgress (SSE)

8.2 Re-dispatch после watchdog

Watchdog (reconcileCycle → checkStalledAudioScenes) → audioOrch state: WAITING_CHUNKS, last_chunk_at + 5min < now → audioOrch.failWaitingScene() └─ orchestrator.failStage('audio') → asset.audio = FAILED → audio-orch = FAILED (синхронно) → asset.audio = PENDING (re-dispatch) → finalizeDispatch(failure) Scheduler tick (next) → asset.audio = PENDING → stages=['audio'] → dispatchStage('audio') └─ orchestrator.setSceneGenerating('audio') → audio-orch FAILED → GENERATING (valid transition!) ... генерация заново

8.3 Regenerate (dirty scene)

User edits text, clicks "Generate" → /api/v1/regenerate → orchestrator.resetScenes() → clearLeases, clear queues └─ orchestrator.markDirtyScene('audio') → audio-orch DONE? → deleteState (clean slate) → asset.audio = DIRTY → scheduler.addSceneToActiveIndex() Scheduler tick → asset.audio = DIRTY → stages=['audio'] → dispatchStage('audio') → orchestrator.setSceneGenerating('audio') → audio-orch: no state → initPlaceholderReady → asset.audio = GENERATING → audioOrch.setGenerating() → dispatch to GPU

8.4 Stale recovery (WAITING_CHUNKS → reset)

После рестарта или сбоя: → audio-orch в WAITING_CHUNKS (от предыдущей незавершённой генерации) → Scheduler видит asset.audio = GENERATING (остался от прошлого раза) → dispatchStage('audio') → orchestrator.setSceneGenerating('audio') → setGenerating() → FAILS (WAITING_CHUNKS → GENERATING invalid) → stale-phase recovery: → deleteState (только если WAITING_CHUNKS/GENERATING/FAILED) → initPlaceholderReady → setGenerating ✅ → dispatch to GPU (свежая генерация)

scene-restoration → через version gate 🔴 Прямой вызов setAssetState(audio, READY)
Циклическая зависимость orchestration↔runtime 🔴 Разрыв через index.js — хрупкое равновесие

Тестовые сценарии из документа — покрытие

#СценарийПокрытие
1Штатная генерация: PLACEHOLDER_READY → ... → DONE + READY✅ happy-path
2Watchdog: WAITING_CHUNKS → FAILED → PENDING✅ runtime-timeouts
3Re-dispatch: FAILED → GENERATING → ... → DONE✅ happy-path
4Regenerate: DONE → deleteState → DIRTY → PENDING → DONE⚠️ Частично

12. Рекомендации

🔴 Приоритет 1: Устранить циклическую зависимость

Внедрить DI/интерфейсы между orchestrator.js и dispatch-engine.js. Сейчас разрыв через index.js — хрупкое равновесие. Цель — чтобы ни один модуль не делал require другого напрямую.

⚠️ Приоритет 2: Прогнать scene-restoration через version gate

scene-restoration.js пишет state.setAssetState(audio, READY) в обход фасада, минуя version gate. Добавить вызов orchestrator.completeStage (или хотя бы проверку PG версии) перед установкой READY.

⚠️ Приоритет 3: Мониторинг lease renewal timer'ов

Добавить метрики в lease-manager.js: количество активных таймеров, количество утечек (таймер без lease), gc-коллбек. Рассмотреть использование одного setInterval вместо множества setTimeout.

💡 Приоритет 4: Обновить тесты для новых фич

Последние изменения (checkStalledAudioScenes с disk recovery, DONE guard, event-driven completeChunk) не покрыты тестами. Добавить тесты для:

  • Watchdog с полным/частичным набором чанков на диске
  • DONE guard (предотвращение re-dispatch готового аудио)
  • Version gate stale → DIRTY (не READY)

💡 Приоритет 5: Аудит оставшихся 4 прямых писателей

Проверить, можно ли провести через фасад 4 оставшихся прямых вызова state.setAssetState:

  • runtime-persistence.js — snapshot restore (вероятно, легитимен)
  • debug-routes.cjs — debug (легитимен)
  • redis-helpers.cjs — утилита (можно через фасад)
  • scene-restoration.js — нужно срочно (bypass gate)
