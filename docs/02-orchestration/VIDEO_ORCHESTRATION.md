## 1. Problem It Solves

### Incident 2026-08-11 (book `import_1786345731767_1786345734345`)

Scene `sc-45d38693` split into 5 groups (`_g1`..`_g5`). All 5 generated by
ComfyUI and arrived at gpu-hub → backend (10:37–10:49). But only the first
chunk made it to disk, the other 4 were lost.

**Loss Chain (confirmed from logs):**

```
ComfyUI → gpu-hub → backend (all 5 chunks arrived)
  → first result: completeStage('video') → finalizeDispatch → metadata+lease deleted
  → g2..g5: verifyDispatchIdentity → no_active_dispatch → REJECTED, files not written
```

The cause was "first one takes all" video result handling:

- `completeStage('video')` was called on the **first arriving** result.
- `finalizeDispatch` deleted metadata/lease — dispatch "completed."
- Other groups arrived with their (now stale) `dispatch_id` →
  `verifyDispatchIdentity` → `no_active_dispatch` → result silently dropped.

### Root Architectural Defect

- Scenes became long (28.07, commit `24c2a3e`: `SCENE_TARGET_SEC 20→60`,
  scenes up to 120 sec), splitting into ~20-sec groups (`_g1.._gN`) — normal.
- But multi-group result handling was never implemented:
  `video-merge.js` (`mergeSceneVideoGroups` — ffmpeg concat) was dead code,
  and result handling worked as if for a SINGLE group.
- Before 27.07 scenes were short (1 group = 1 job), so the defect didn't manifest.

## 2. Architecture: `video-orchestrator.js` (Mirror of audio-orchestrator)

### State Machine

```
GENERATING ──→ WAITING_CHUNKS ──→ MERGING ──→ DONE
      │              │               │
      └──→ FAILED ←──┴───────────────┘
```

- **Key:** `animastor:video-orch:{bookId}:{chapterId}:{sceneId}`
- **Stores:** `phase`, `groups` (per-group: `{ unit_ids, status, job_id }`),
  `groups_received`, `build_id`, `dispatch_id`, `started_at`, `last_group_at`.
- **Transitions** (validated, invalid transition → throw):
  - `GENERATING → WAITING_CHUNKS` — after sending jobs
  - `WAITING_CHUNKS → MERGING` — last group arrived → start concat
  - `MERGING → DONE` — concat succeeded → `completeStage('video')`
  - `GENERATING/WAITING_CHUNKS/MERGING → FAILED` — error/stall/cancel
  - `FAILED → GENERATING/WAITING_CHUNKS` — re-dispatch

### How It Differs from Audio

| Aspect | Audio | Video |
|--------|-------|-------|
| Chunks | mp3 files, concat mandatory in pipeline | mp4 files `_gN.mp4`, concat **only for player** |
| After all chunks arrive | merge → DONE | merge → DONE (but group files **preserved**) |
| Dependency on other stages | none | waits only for `image=ready` of **own** scene (reference images) |
| Dirty-regeneration | all scene chunks regenerated | only groups with dirty units |

### Files

```
{build_id}/{book}/{ch}/{scene}_g1.mp4   ← group 1 (first also gets suffix!)
{build_id}/{book}/{ch}/{scene}_g2.mp4   ← group 2
...
{build_id}/{book}/{ch}/{scene}.mp4      ← CONCAT RESULT (only for player)
```

**Naming decision:** first group got suffix `_g1` (was `g1`).
`scene.mp4` is now reserved for concat result — this allows
`mergeSceneVideoGroups` to re-concat correctly without duplicates and makes
`resolveSceneVideoFile` deterministic (concatenated file, otherwise first group file).

Blast radius verified: `parseJobId` (job-schema), `resolveAssetPath` (cleanup-service)
and `worker.cjs` (writes base64, backend forms filename) already understand `_gN`;
gpu-hub is transparent to job_id.

## 3. Call Flow

### 3.1 Dispatch (`executeVideoDispatch` in scene-orchestrator.js)

```
Scheduler tick → dispatchStage('video')
  → acquireLease + quota
  → executeVideoDispatch():
     1. Reads PREVIOUS video-orch state (for dirty-regeneration)
     2. videoOrch.initState(groups)      — group composition, unit_ids
     3. Loop over groups:
        - dirty units from PG (getDirtyUnitIds) → group is dirty
        - group composition changed → dirty
        - otherwise cache-hit → markGroupDone without sending
     4. Send only dirty groups → gpu-hub (job_id = {scene}_gN:video)
     5. videoOrch.setWaitingChunks()
     6. All groups in cache → fast-track: completeGroup → concat without jobs
  → return { dispatched, jobs, reason }
```

### 3.2 Result Receipt (`completeGroup`)

```
POST /gpu/task/result → handleTaskResult (stale-accept for video)
  → parseJobId → kind='scene_video', groupSuffix='_g2'
  → videoOrch.completeGroup({ job_id, build_id, dispatchId, result_base64 })
     1. Validation: state exists, group in list
     2. Write file {scene}_g2.mp4 to disk (+ size check)
     3. markGroupDone → groups_received++
     4. Not all groups → stay in WAITING_CHUNKS
     5. All groups → WAITING_CHUNKS → MERGING:
        mergeSceneVideoGroups (NX lock; race loser gets null → waits)
        → MERGING → DONE → orchestrator.completeStage('video')
        → finalizeDispatch(success) → asset.video = READY
```

### 3.3 Stale-Accept (Key Fix)

Like audio: a late group with **old** `dispatch_id` is accepted while scene is
in `WAITING_CHUNKS/MERGING`. `completeGroup` uses `dispatch_id` from CURRENT
metadata — so `verifyDispatchIdentity` in `completeStage` doesn't break.

Implemented in two locations:
- `routes/generation-routes.cjs` — `/gpu/task/result`
- `services/task-handler.cjs` — `scene_video` branch

## 4. Dirty-Regeneration (Targeted)

Mapping `unit_ids → group` stored in state (`groups[].unit_ids`).

```
Unit 1 + Unit 2 + Unit 3 → Video Chunk 5   (groups[5].unit_ids = [u1, u2, u3])

Change Unit 2:
  → PG: getDirtyUnitIds(scene) = [u2]
  → executeVideoDispatch: group 5 contains u2 → dirty
  → regenerate ONLY group 5 (same prompt mechanism
    + injection of reference images for group units)
  → cache-hit groups marked done without sending jobs
  → full cache → fast-track merge (scene rebuilt without a single job)
```

Group boundaries are recalculated by duration (duration-aware chunking) —
a group with **changed composition** is also considered dirty.

## 5. Recovery and Invariants

### Watchdog (`checkStalledVideoScenes`, reconcileCycle)

- Stall threshold — **dynamic**: actual `video_timeout_minutes` from
  layer-config (fallback `VIDEO_CHUNK_STALL_MS`), threshold = timeout + margin.
  Not fixed 60 min — otherwise watchdog could fail live generation
  before per-job timeout.
- Stall → `failWaitingScene` → clears hub-dedup for missing groups →
  `FAILED → PENDING` → re-dispatch.

### Startup Recovery (`recoverVideoOrchStates`)

- After restart, resumes states in `GENERATING/WAITING_CHUNKS/MERGING`.

### Invariants (`checkVideoOrchInvariants`)

```
video-orch.phase == DONE  ⇔  asset.video == READY   [always true]
video-orch.phase == FAILED ⇒  asset.video ∈ {FAILED, PENDING}
video-orch.phase ∈ {GENERATING, WAITING_CHUNKS, MERGING}
                         ⇒  asset.video == GENERATING
```

### Delete-on-Reject (`recoverResultKeys`)

Terminally rejected results (`no_active_dispatch`, `stale_dispatch`, etc.)
are **deleted from Redis** instead of infinite retry every 60 s.

### Merge-Lock Guard

Two simultaneously arriving results don't corrupt scene into FAILED: `mergeSceneVideoGroups`
is protected by NX lock, loser gets `null` → stays in `WAITING_CHUNKS` waiting for
the winner. Real concat failure is a throw (→ FAILED), not `null`.

## 7. Long Video Generation Timeouts

### Problem

Video generation is architecturally slow: LTX 2.3 — already ~190 s now, 5–10 min
normal, 20–30+ min on weak consumer GPU. Three links had short fixed ceilings:

| Link | Was | Problem |
|------|-----|---------|
| gpu-hub | `timeout_ms` not read from body → per-job timeout = `GPU_TIMEOUT_MS` (10 min) | video >10 min killed as `worker_timeout` |
| worker | `RESULT_TIMEOUT_MS = 600000` (10 min), `task.timeout_ms` ignored | worker killed normal long generation |
| watchdog | fixed threshold 60 min | could fire before actual per-job timeout (up to 180 min) |

### Fixed

```
backend (layer-config: video_timeout_minutes, default 60, range 10–180)
  → gpu-hub: POST /task body.timeout_ms → queue task.timeout_ms + running.timeout_ms
     per-job timeout = timeout_ms || GPU_TIMEOUT_MS
     guard: per-job timeout ≥ GPU_TIMEOUT_MS
  → worker: waitResult(prompt_id, workflow, task.timeout_ms)
     priority: task.timeout_ms
     video-fallback: VIDEO_RESULT_TIMEOUT_MS (default 2 hours, env)
     others: RESULT_TIMEOUT_MS (unchanged)
  → watchdog: threshold = layer-config video_timeout_minutes + margin
```

**Principle:** distinguishing "generation is running long" from "stuck / worker dead"
is determined ONLY by per-job timeout from layer-config (user setting),
not an arbitrary short default.

### image/video Parallelism (Verified, No Changes Needed)

- Image and video are independent stages (`shouldScheduleAssets`): no global
  "wait until all images."
- Video for a scene waits only for `image=ready` of **own** scene (reference images
  for injection into workflow).
- "Scene 1 / Chunk 1 waiting for image" does NOT block "Scene 2 / Chunk 3 → video"
  or "Scene 3 → image."

## 8. Live Test 2026-08-11: What Was Found and Fixed

Full E2E run of scene `sc-45d38693` (5 groups, 1 unit each) confirmed the
entire chain works and surfaced 3 issues:

### 8.1 Chain Worked Completely

```
VIDEO_DISPATCH groups=['_g1'..'_g5'] (timeout=60 min from layer-config)
📥 Task _g1.._g5:video timeout_ms:3600000   → all 5 in hub queue
🚀 _g1.._g5 → gpu-n-94d62b6a (video)        → worker
📤 Result _g1.._g5 (2.95–9.59MB)            → ALL 5 arrived, each ~3 min
[VIDEO-ORCH] 5/5 groups received
[VIDEO-MERGE] mergeSceneVideoGroups suffixes=[_g1.._g5]
[VIDEO-ORCH] DONE (5 groups merged → scene.mp4)
[ORCH] [PG-VIDEO-READY] status=ready        → asset.video = READY
```

Yesterday's "only first chunk arrived" incident no longer reproduces:
all 5 groups saved as separate files `_gN.mp4`, concat into `scene.mp4`
(23MB) happened only after ALL groups arrived, player serves complete video.

### 8.2 Issues Found During Test (And Fixes)

1. **Stale `image=generating` blocked video (not code, data).** After
   gpu-hub restart, image worker got `💀 GPU timeout` and died; `iu-in-flight`
   keys expired by TTL, but asset-state `image=generating` remained →
   `imageEnabled=true` (in-flight) → video not dispatched (waits `image=ready`
   of own scene — local dependency works as designed). Unblocked manually:
   `HSET image=ready` (images already on disk and registered).
2. **Fast-track merge fell with `orchestrator is not defined`** (our bug): in
   `executeVideoDispatch` variable `orchestrator` was not imported
   (only destructuring `{ completeStage, ... }`), but `completeGroup`
   requires `deps.orchestrator`. Fix: `const orchestrator = require('./orchestrator')`.
3. **VERSION-GATE: legacy books without `scenes` row in PG didn't get READY**
   (pre-existing): `completeStage` fail-closed — `SELECT content_version`
   → 0 rows → `shouldWriteReady=false` → DIRTY → infinite loop
   `dirty → fast-track → DONE → dirty`. But `scene_assets` video row is created
   only by `markReady`, which is called AFTER gate — closed loop.
   Fix: when 0 rows in `scenes`, gate passes (scene without version schema
   can't go stale); fail-closed for real schemas preserved.

### 8.3 Operational Notes for Tests

- Before test, rebuild **gpu-hub** (`docker compose up -d --build gpu-hub`)
  — otherwise old hub (without live-mount) won't pass `timeout_ms` and will kill
  long videos at 10-min GPU_TIMEOUT.
- Workers on GPU instance must have current `worker.cjs` (from push).
- To bypass dead image worker during test, unit image was substituted with
  copy of neighbor (data, not code) — on next normal generation
  the real one will be generated.
