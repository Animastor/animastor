**Проект:** Animastor
**Дата:** 2026-07-08
**Frontend:** Android (Kotlin, ~14 600 строк), пакет `com.example.animastor`
**Backend:** Node.js / Express (модульный), Redis + PostgreSQL, GPU-оркестрация

## 0. Резюме (TL;DR)

Frontend — это нативный Android-клиент, а не «тонкий» слой отображения. За время развития
в него утекло значительное количество **бизнес-логики**, которая должна принадлежать серверу:
вычисление профиля генерации, конечный автомат прогресс-панели, инференс прогресса VBook
из русскоязычного текста регэкспами, решение о триггере следующего окна генерации,
нумерация глав, сборка system-prompt для чата и реконсиляция правок.

Ключевой вывод: **бэкенд уже содержит эталонные версии части этой логики** (например,
`resolveProfile()` в `layer-config.js` — точная копия клиентского `computeProfile()`),
но не всегда её отдаёт, из-за чего клиент дублирует вычисления. Это самый дешёвый и
безопасный класс переносов: логика уже написана на сервере.

При появлении второго/третьего клиента (Web, Desktop) вся эта логика будет переписана
заново на каждой платформе — с неизбежным расхождением поведения. Это главный аргумент «за».

**Оценка объёма:** из ~14 600 строк фронта потенциально устраняется/упрощается ~1 500–2 000 строк
логики. Самые тяжёлые файлы (`GenerateViewModel` 1744, `PlaybackViewModel` 926,
`EditFragment` 1228) худеют сильнее всего.

Приоритизированный список задач — в разделе 4.

## 1. Принцип классификации

Для каждого участка задаём 5 вопросов из ТЗ. Чтобы не раздувать отчёт, они сведены в поля:
**Где / Сейчас / Через backend / Плюсы / Минусы / Рекомендация / Сложность**.

Что **остаётся на клиенте по определению** (легитимная клиентская ответственность,
не выносим):

- Тайминги воспроизведения, буферизация, чейнинг `MediaPlayer`, громкость, seek.
- Циклирование IU-картинок под позицию плеера (реальное время, локальный `MediaPlayer.position`).
- Восстановление после поворота экрана (локальный sequence-счётчик).
- Расчёты вёрстки (высота карточек от плотности экрана, аспект).
- Анимация «печатает…», индикаторы набора.
- Маппинг `status → цвет/строка` и `dataType → InputType` (локализация и UI-виджеты).
- Сериализация в `Bundle` между фрагментами (ограничение Android).

Всё это в отчёте помечено как **KEEP** и далее не детализируется.

## 2. Находки (по убыванию ценности)

### F1. Вычисление профиля генерации — точный дубль серверной логики 🔴

- **Где:** `GenerateViewModel.kt:195–211` (`computeProfile()`), плюс использования
  `250–264` (`persistLayerConfig`), `259`, `307–315`.
- **Сейчас:** клиент из трёх булевых флагов (audio/image/video) вычисляет строку профиля
  (`full` / `storyboard` / `image_only` / `audio_only` / `video_only`) 8-ветвным `if`.
- **Через backend:** эта функция **уже существует** — `backend/src/services/layer-config.js:77–84`
  (`resolveProfile`). Более того, `PUT /api/v1/book/{id}/layer-config` и
  `AssetsStateResponse` **уже содержат поле `profile`** (см. `LayerConfig.kt`).
  Клиент должен просто читать `response.profile`, отправляя только тумблеры.
- **Плюсы:** удаление дублирующего инварианта; единый источник правды о том, что такое
  «профиль»; новые клиенты не переписывают таблицу из 8 состояний.
- **Минусы:** практически нет. Нужно гарантировать, что все ответы, где нужен профиль,
  его возвращают (сейчас `assets-state` в `chunks-routes.cjs` его **не** кладёт в JSON —
  надо добавить одно поле).
- **Рекомендация:** **ПЕРЕНЕСТИ.** Это чистый выигрыш: убираем мёртвый код,
  дублирующий уже написанную серверную функцию.
- **Сложность:** очень низкая (backend: +1 поле в `assets-state`; frontend: удалить функцию).

### F2. Конечный автомат прогресс-панели («воркеры») 🔴

- **Где:** `GenerateViewModel.kt:1378–1576` — `computeWorkers()` (~170 строк),
  `getProgressTotal()` (1378–1385), `getAnyLayerIncomplete()` (1387–1396),
  плюс поля состояния `workerReadyFloor`, `workerCompletedAt`, `_workerPermanentlyDone`,
  `gpuProgressDoneAt`.
- **Сейчас:** клиент из «сырого» `AssetsStateResponse` собирает список воркеров и их
  проценты. В логике зашиты бизнес-правила:
  - какие слои видимы при каком профиле (`audioNeeded = profile in [...]`);
  - выбор счётчика IU vs legacy image (`if scope_iu_total > 0`);
  - монотонный «пол» прогресса, чтобы % не откатывался;
  - тайминги «показать Done 10 c и скрыть» (`COMPLETED_WORKER_DISPLAY_MS`);
  - вычисление процента `r * 100 / total`, done-детект `r >= total`.
- **Через backend:** ввести эндпоинт/поле `progress` (или расширить `assets-state`),
  который возвращает **готовый массив воркеров**: `[{type, ready, total, percent, done,
  visible, indeterminate, label_key}]` и агрегаты `overall_percent`, `any_incomplete`.
  Правила «видимости слоя при профиле» и «IU vs image» уже известны серверу (он же
  генерирует). Монотонность прогресса backend тоже может гарантировать.
- **Плюсы:** самая сложная и хрупкая часть фронта (регулярный источник багов — см.
  git-историю: «scene counter 1/1», «broken counter», «Idle leaking») уходит на сервер;
  консистентность между клиентами; проще тестировать (серверные unit-тесты уже есть —
  `iu-progress-utils.test.js`).
- **Минусы:** тайминги показа «Done N секунд» — это UI-политика; её лучше оставить на
  клиенте (клиент решает, сколько держать завершённую строку). То есть переносим
  *вычисление* состояния, но не *косметику показа*. Небольшой риск роста числа полей в ответе.
- **Рекомендация:** **ПЕРЕНЕСТИ вычисление** (проценты, видимость, done, монотонность,
  выбор IU/image). **Оставить** только длительность подсветки «готово» на клиенте.
- **Сложность:** средняя (backend: агрегатор поверх уже существующего `assets-state`;
  frontend: заменить `computeWorkers` на рендер готового списка).

### F3. Инференс прогресса VBook регэкспами по русскому тексту 🔴

- **Где:** `GenerateViewModel.kt:968–1024` (`updateVBookProgress`) и `1293–1315`
  (обработка SSE-события); маппинг `step_type → VBookStage` (969–976).
- **Сейчас:** клиент **парсит человекочитаемое сообщение** прогресса регэкспом
  `Regex("""сцен[ыа][\s]*?(\d+)""")`, затем каскадом `?:`-фолбэков и модульной
  арифметикой (`((globalScene - 1) % windowTotal) + 1`) восстанавливает индекс сцены
  в окне, стартовую сцену окна и общее число. Это инференс серверного состояния из
  его же логов.
- **Через backend:** SSE-событие `vbook` должно нести **уже посчитанные** числовые поля:
  `stage`, `window_scene_index`, `window_total_scenes`, `window_start_scene`,
  `global_scene_index`. Часть полей уже есть в событии (клиент их читает первым приоритетом);
  задача — гарантировать их всегда и **убрать регэксп-фолбэк**.
- **Плюсы:** устранение самого хрупкого места (парсинг локализованной строки — ломается
  при смене формулировки; git-история подтверждает поломки счётчика); i18n перестаёт
  влиять на логику; новые клиенты не парсят русский текст.
- **Минусы:** нужно навести порядок в схеме SSE-события на сервере (единый контракт).
  Практически нет downside по производительности.
- **Рекомендация:** **ПЕРЕНЕСТИ.** Регэксп по локализованному сообщению — явный анти-паттерн.
- **Сложность:** низкая–средняя (backend: заполнять поля события; frontend: удалить парсинг).

### F4. Решение о триггере следующего окна генерации 🔴

- **Где:** `WindowTriggerManager.kt:93–179` (`checkEndOfWindow`), 180 строк целиком.
- **Сейчас:** клиент по позиции плеера решает, когда дёрнуть `trigger-next-window`:
  - юнит должен быть среди последних 3 сцены (`last3Start`);
  - позиция должна совпадать с «фронтиром генерации» — клиент **перебирает все главы/сцены**,
    фильтрует `chapter_intro`/`cover`, находит последнюю сцену;
  - дедуп по ключу окна (`triggeredWindows`), one-shot по юниту, cooldown 60 c.
- **Через backend:** эндпоинт `POST /trigger-next-window` **уже существует**
  (`import-routes.cjs:361`). Клиенту достаточно **сообщать текущую позицию**
  (он и так её знает), а решение «пора / не пора / already done» принимает сервер,
  который владеет истинным фронтиром, дедупом и rate-limit. Идеально — сервер возвращает
  в прогресс-стриме флаг `should_prefetch_next` либо просто делает всё сам по позиции.
- **Плюсы:** дедуп и cooldown становятся серверным состоянием (переживают краш/поворот
  клиента, не гоняются повторно с нескольких клиентов); фронтир не дублируется; ~130 строк
  клиентской логики удаляются; поведение одинаково на всех платформах.
- **Минусы:** повышается частота сообщений о позиции на сервер (можно слать троттлингом
  раз в N секунд — дёшево). Нужно аккуратно с идемпотентностью (сервер и так её обеспечивает
  через leases — см. `lease-manager.js`).
- **Рекомендация:** **ПЕРЕНЕСТИ решение.** Клиент шлёт позицию; «last-3 / frontier / dedup /
  cooldown» — на сервере.
- **Сложность:** средняя (нужен канал позиции + серверная оценка; сам триггер-эндпоинт готов).

### F5. Нумерация глав и сборка меток позиции (дублируется 3×) 🟠

- **Где:** `NavigateFragment.kt:185–217, 258–301`; `EditFragment.kt:237–272`;
  `AiAssistantFragment.kt:684–730` — один и тот же расчёт в трёх местах.
- **Сейчас:** клиент считает «реальный номер главы», исключая `cover`/`prologue`:
  `chapters.take(chIdx).count { it.type != "cover" && it.type != "prologue" } + 1`,
  усекает заголовки (`take(60)`), нормализует переносы, строит вложенные условные метки
  «Глава X / Сцена Y — Title / Юнит Z».
- **Через backend:** сервер уже нумерует главы внутри (`chapter-utils.js:10`
  `createChapterIntroScene(chapterTitle, chapterNumber, …)`), но **не отдаёт** display-номер.
  Добавить в модель книги поля `display_number` (глава), `display_index` (сцена/юнит) и
  готовую `path_label` при отдаче `getBook`. Клиент только подставляет локализованные
  слова «Глава/Сцена/Юнит».
- **Плюсы:** устраняется тройное дублирование и риск расхождения; правило «cover/prologue
  не считаются» — бизнес-правило, ему место на сервере.
- **Минусы:** локализация слов «Глава/Сцена» остаётся на клиенте (правильно). Сервер отдаёт
  номера/индексы, клиент — слова. Небольшое увеличение модели книги.
- **Рекомендация:** **ПЕРЕНЕСТИ вычисление номеров/индексов** (числа и структура), слова —
  KEEP на клиенте ради i18n.
- **Сложность:** низкая–средняя.

### F6. Сборка system-prompt для AI-чата на клиенте 🟠

- **Где:** `AiAssistantFragment.kt:666–800` (`sendMessage`), сборка в `746–748`;
  языковая инструкция `739–744`; резолв позиции `684–730`.
- **Сейчас:** клиент склеивает полный system-prompt: имя приложения + режим
  (`mode.systemPrompt`) + топик (`topic.systemPrompt`) + резолвнутая позиция +
  языковая инструкция (`when(lang) "ru"/"en"/"auto"`). Определения режимов/топиков
  зашиты в клиенте (`AssistantMode.kt`, `ChatTopic.kt`).
- **Через backend:** клиент шлёт `{ sessionId, mode, topic, message, position }`; сервер
  сам собирает system-prompt из своих определений режимов/топиков и языка сессии.
  У сервера уже есть `services/agent-prompts.js` и SSE-чат (`ai-routes.cjs:292`).
- **Плюсы:** промпты (ядро продукта) редактируются на сервере без релиза приложения;
  единый промпт для всех клиентов; секьюрити (правила промпта не «зашиты» в APK).
- **Минусы:** меньше гибкости у клиента формировать промпт офлайн; нужно передавать
  позицию/режим в структурированном виде. Определения режимов/топиков для *отображения*
  (названия, иконки) могут остаться на клиенте.
- **Рекомендация:** **ПЕРЕНЕСТИ сборку промпта.** Клиент отправляет параметры, не текст промпта.
- **Сложность:** средняя.

### F7. Разбор заголовка главы из текста интро (`enrichTitles`) 🟠

- **Где:** `BookModels.kt:133–145` (`extractChapterTitleFromIntro`), `405–433`
  (`enrichTitles`); вызывается по всему фронту (`NavigateFragment:234`,
  `AiAssistantFragment:348,508`, и т.д.).
- **Сейчас:** клиент, если `chapter_title == null`, парсит текст интро по списку
  разделителей `[" — ", " – ", ". ", "! ", "? "]`, вырезает кандидата, чистит пунктуацию.
- **Через backend:** заголовок главы должен вычисляться при парсинге книги на сервере и
  сохраняться в модель (`parse.js` уже проставляет `chapter_title` из `chInfo.title`).
  `getBook` должен всегда отдавать заполненный `chapter_title`, а не заставлять клиент

- **Плюсы:** убирается строковая эвристика с клиента; консистентность; `enrichTitles()`
  вызывается десятками мест — все упрощаются.
- **Минусы:** нужно прогнать эвристику на сервере для старых книг (миграция/лениво при чтении).
- **Рекомендация:** **ПЕРЕНЕСТИ.**
- **Сложность:** низкая (логика короткая, портируется 1:1 в `lazy-book/parse.js`).

### F8. Реконсиляция правок сцены: dotted-path merge, роутинг патча, каскад таймингов 🟠

- **Где:** `EditFragment.kt` — `applyFieldValues` (766–839, слияние плоской карты полей в
  вложенные `LocationData`/`EnvironmentData`, `participants = v.split(", ")`),
  роутинг «unit-only vs full scene» (878–901), каскадный пересчёт таймингов
  (`handleRangeChange` 1142–1177), клэмпинг границ (1044–1049).
- **Сейчас:** клиент знает схему сущностей (какие поля куда вложены), сам решает формат
  патча, сам пересчитывает тайминги всех последующих юнитов при сдвиге одного и клэмпит
  границы в валидный диапазон.
- **Через backend:** отправлять **плоский набор изменённых полей** (`{path: value}`) на
  сервер; сервер собирает вложенную структуру по схеме (у него есть `workflows/entity-schema.js`),
  сам определяет минимальный патч и **сам пересчитывает каскад таймингов** (эндпоинт

- **Плюсы:** знание схемы сущностей уходит с клиента (сейчас оно продублировано с сервером);
  каскад таймингов — чистое бизнес-правило; меньше шансов рассинхрона при добавлении полей.
- **Минусы:** редактор может стать чуть менее «отзывчивым» (каскад считает сервер) — решается

- **Рекомендация:** **ПЕРЕНЕСТИ merge/валидацию/каскад**; локальный предпросмотр перетаскивания — KEEP.
- **Сложность:** средняя–высокая (самый связный кусок редактора).

## 5. Общие рекомендации по контракту

1. **Не отдавать «сырьё» под клиентский расчёт.** Если сервер знает ответ (профиль, номер
   главы, процент, готовность) — отдавать готовое значение, а не поля для вычисления.
2. **Локализация ≠ бизнес-логика.** Числа/структуру/решения считает сервер; слова
   («Глава», «Сцена») и цвета подставляет клиент.
3. **Push вместо poll.** Там, где клиент опрашивает и решает «готово ли» (F10/F11) —
   заменить на терминальные SSE-события. Backoff-поллинг как fallback — оставить.
4. **Единый источник правды для схем.** Схема сущностей (`entity-schema.js`) и определения
   профилей/режимов должны жить только на сервере; клиент их не дублирует.
5. **Версионировать контракт.** При выносе логики добавлять поля не ломая старый клиент
   (аддитивно), чтобы APK и будущий Web могли сосуществовать.
