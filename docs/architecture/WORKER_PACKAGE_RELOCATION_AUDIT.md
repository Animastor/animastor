## Executive summary

The Worker runtime bundle is **already a standalone package in every technical sense** (zero npm deps, require-containment guarded, generated protocol copy committed, `npm pack` → clean-dir boot verified during this audit). The ONLY thing that distinguishes it from the four migrated modules is its **physical address** `worker/worker/`.

The Phase 9D decision (commit `3fefcbda`, one day before this audit) kept that address deliberately: all four deployment channels + ~20 test pins referenced it, and moving it would have broken deployment "for zero runtime benefit". That decision was **correct for its moment** — but it is a *deployment-coordinate* constraint, not a *technical invariant* of the bundle. Since 9D, three modules with comparable (contracts: compose mount + facade; gpu-hub: Dockerfile + compose + 15 test files) or larger coupling were moved into `packages/` the same day, each as a single atomic commit. The Worker is now the **only standalone module outside `packages/`**.

**Verdict: MOVE AFTER PREPARATION.** The move is feasible and has a known-good playbook, but unlike the completed moves it touches **two-sided production artifact format** (hub installer-tar layout ↔ installer engine repo fallback), **shipped manifest data** (×3), **the hub Dockerfile bake-in**, and **~20 test pins incl. two deployment-wiring guards (D7, phase10t-1)**. It cannot be done under the current audit's own constraints (deployment wiring must not change); it must be its own phase with a coordinated commit and a full regression run.

## 3. Phase 9D — historical reason and current validity

**What 9D decided (commit `3fefcbda`, 2026-09-06; audit doc §1.4, §7):**
"The catalog was NOT moved. All four channels (and ~20 test pins) already point at `worker/worker/`; moving it would give zero runtime benefit and break deployment (violating the constraint 'do not remove the old deployment path'). Physical extraction was realized through the package contour, not a directory rename." Rollback = `git revert`.

**Was it a technical invariant?** No — it was a **risk decision under phase constraints**:
- The bundle itself has zero path dependencies: D3 require-containment (no require escapes the bundle), zero npm deps, standalone boot proven at 9D and re-proven in this audit.
- Every channel reference is a config string, manifest field, Dockerfile line, or test pin — i.e. *coordinates*, all repo-internal, all updatable in one commit.
- The stated blocker was scope/rollback safety within the 9D phase, not impossibility.

**Is it still valid today?** As a *permanent architecture rule* — no:
1. Since 9D, the repo executed the MODULE_LAYOUT_MIGRATION_AUDIT plan: `ai-connector` → packages (`9fef24ba`), `contracts` → packages (`4ed7f8f5`), `gpu-hub` → packages (`e68beea0`) — the last two had compose mounts/Dockerfiles/guards of comparable coupling, moved atomically with full pin updates. `packages/` is now the established canonical location (root `node_modules` symlinks: `@animastor/contracts`, `animastor-ai-connector`, `animastor-comfyui-workflow-connector`).
2. The Worker is now the **only** standalone module outside `packages/` — the inconsistency the migration audit predicted ("accepted inconsistency") has become an outlier.
3. The 9D constraint doc itself says the deployment channels are "channels of artifact DELIVERY, not code dependencies" (§10.1) — i.e. the coupling is exactly the kind already overcome three times.
4. One real new fact since 9D: the worker package went **public-ready** (9E: `private` removed, repository metadata added) — strengthening the case for the standard location, since `repository.directory` metadata ships to npm.

**What remains true:** the *relocation* still must update P1–P9 + T1–T17 in one coordinated commit; D7/phase10t-1 must be consciously re-pinned (they exist to catch accidental unwiring, and a move IS a rewiring — update them in the same commit, never delete).

**Classification: OUTDATED (as invariant) / honored-so-far (as status).**

## 6. Deployment coupling detail

| Channel | Mechanism | Reads path from | Break mode if half-migrated |
|---|---|---|---|
| Hub image bake-in (production) | Dockerfile stager `COPY worker/worker/` → `/app/artifacts/worker-bundle` | repo build context | image build fails → caught at build (fail-fast verification exists) |
| Local dev overlay | bind mount `./worker/worker:/app/worker-bundle:ro` | compose file | hub serves stale/missing bundle → D7 + phase10t-1 guards scream |
| Hub → GPU delivery | `GET /worker-bundle` tar + sha256 (entries named `animastor-worker/*`) | `WORKER_BUNDLE_DIR` content — **source-path agnostic** | none (path only matters one step earlier) |
| Installer package (offline installs) | hub builds tar with internal layout `animastor-installer/worker/worker/*`; engine inside resolves `repoRoot/worker/worker` | **two-sided string** (P9 ↔ P6/P7) | offline install degrades to hub fetch or fails ("could not obtain bundle files") — silent unless tested |
| Installer repo-checkout fallback | `engine/worker.js` + `engine.js` join | production code | full-install path silently prefers hub fetch (behavior change masked by network) |
| Setup contract version resolver | `setup-contract.js` repo fallback → `worker/worker/package.json` | production code | version falls back to hub probe/null (masked) |
| Manual copy | `worker/worker/` documented in README/.env.example | docs | human confusion only |

Key insight: the **external artifact formats** (hub tar entries `animastor-worker/*`, published npm tarball) do NOT embed the repo path; only the **installer package internal layout** does (P9), and both of its sides are regenerated from the same repo build — so a coordinated rename is safe, but a partial rename is silently dangerous. This is the main reason for MOVE AFTER PREPARATION rather than MOVE NOW.

## 7. Gap analysis vs the `packages/` standard

Compared with the four migrated modules, `animastor-worker` is missing only:

| Standard property (contracts / gpu-hub / ai-connector / comfyui-connector) | Worker today | Gap |
|---|---|---|
| Lives at `packages/animastor-*` | `worker/worker/` (nested inside ops dir `worker/`) | **the relocation itself** |
| README inside package dir | `worker/README.md` (one level above bundle) | moves with the boundary (structure below) |
| Tests inside package dir | `worker/tests/` (outside bundle dir — REQUIRED: hub walkDir ships everything except `.env*` from the bundle dir) | structure question, see §8 |
| root `node_modules` symlink | none (nobody requires the worker; inbound isolation P7-T2 forbids it) | **none needed** — worker is consumed only via artifacts/HTTP |
| npm-publishable | already public-ready (9E) | none |
| repository.directory accurate | says `worker/worker` | one field (W1) |
| referenced by syntax-smoke | `worker` checked at `$ROOT_DIR/worker` | P11 |

Note the structural nuance that makes this move *slightly* different from the previous three: the shipped artifact **is** a directory consumed by `walkDir`, so tests/tools can never sit inside the bundle dir (guard D2). Two viable target layouts:

- **Option A — wholesale boundary move (minimal diff, recommended for the move commit):** `git mv worker packages/animastor-worker` → layout `packages/animastor-worker/{worker/ (bundle), tests/, tools/, README.md, *.sh, new/, image/}`. All internal relative refs (`../worker`, `cd worker`) survive unchanged; only external coordinates (P1–P11, T1–T17, F1–F4, W1–W7) change. Matches today's topology 1:1; ops scripts keep working in repo checkouts.
- **Option B — flat package (target-state cleanup, separate follow-up):** `packages/animastor-worker/` = the 8 bundle files at top + `tests/` + `tools/` + README. Requires a hub-side hardening: replace `isServableBundleFile` (currently "everything except `.env*`") with a strict 8-file allowlist — which also aligns the hub with guard D2 and protects against future stray files. More production churn; do only after Option A has settled.
